# Глава 3. PlaygroundWindow — UIWindow с shake-detect

Когда пользователь зашёл в mini-app — например, в Калькулятор, — он
оказывается «внутри отдельного приложения». Кнопки «← Назад» к
лаунчеру сверху нет: mini-app не кладётся поверх лаунчера в общую
стопку экранов, а **целиком заменяет** его в окне (как именно — в
главе 4). По той же причине не сработает и жест «смахни от левого
края»: он возвращает на предыдущий экран стопки, а предыдущего экрана
у mini-app нет.

Нужен другой способ вернуться. В iOS он уже есть — **встряхивание**
устройства (shake, англ. «трясти»). Система сама использует его для
отмены ввода: набрал текст, встряхнул — iOS спросит «Отменить ввод?».
В симуляторе встряхивание делается сочетанием **⌃⌘Z** (Control +
Command + Z) или через меню **Device → Shake**.

В этой главе делаем своё окно — наследника `UIWindow`, который ловит
встряхивание и сообщает о нём. Никаких сторонних библиотек, десяток
строк кода — плюс понимание **responder chain**, о которой ниже.

## 3.1 Что такое UIWindow и почему его обычно не трогают

**`UIWindow`** — самый верхний контейнер интерфейса. Все экраны
приложения рисуются внутри окна: у окна есть `rootViewController`
(корневой view controller), а у него — свои вложенные экраны и view.
Аналогия: окно — рама картины, `rootViewController` — сама картина.
Картину можно заменить, рама остаётся.

Окно принадлежит **сцене** (`UIWindowScene`) — одному «экземпляру»
интерфейса приложения. На iPhone сцена обычно одна, на iPad
приложение может открыть несколько сцен рядом (подробнее — в главе 5).
Кроме твоего окна система держит и свои: например, клавиатура и
системные алерты рисуются в отдельных окнах поверх твоего.

В большинстве проектов окно создают одной строкой и забывают:

```swift
window = UIWindow(windowScene: windowScene)
```

Дальше с окном не работают — все экраны живут внутри
`rootViewController`.

Нам этого мало: мы хотим, чтобы окно само замечало встряхивание.
Поэтому делаем наследника — `PlaygroundWindow`.

## 3.2 Минимальный наследник

Файл: `App/PlaygroundWindow.swift`. Весь класс — десять строк:

```swift
import UIKit

/// Окно, которое сообщает о встряхивании устройства.
final class PlaygroundWindow: UIWindow {

    var onShake: (() -> Void)?

    override func motionEnded(_ motion: UIEvent.EventSubtype, with event: UIEvent?) {
        super.motionEnded(motion, with: event)
        guard motion == .motionShake else { return }
        onShake?()
    }
}
```

Разберём.

- `var onShake: (() -> Void)?` — callback: опциональное замыкание без
  параметров. Кто хочет реагировать на встряхивание, кладёт сюда
  функцию. Никто не положил — `nil`, и встряхивание ничего не делает.
- `motionEnded(_:with:)` — метод класса `UIResponder` (о нём — в
  разделе 3.3). UIKit вызывает его, когда **движение закончилось**:
  человек встряхнул телефон и перестал. Есть и парный
  `motionBegan(_:with:)` — «начал трясти», — но нам важен момент, когда
  жест завершён.
- `super.motionEnded(motion, with: event)` — передаём событие дальше,
  как сделал бы `UIWindow` без нашего наследника. Зачем — чуть ниже.
- `guard motion == .motionShake` — проверяем, что это именно
  встряхивание. Тип `UIEvent.EventSubtype` описывает не только движения:
  в нём есть и подтипы для кнопок гарнитуры и пульта (`remoteControlPlay`,
  `remoteControlPause`…). Из «движений» встряхивание — единственное, но
  проверка ничего не стоит и защищает от сюрпризов.
- `onShake?()` — вызываем callback, если он есть. Знак `?` — вызов
  опционального замыкания: если `onShake == nil`, ничего не произойдёт.

Про `super`. Встряхивание нужно не только нам: на нём работает
системная отмена ввода. Её обрабатывает объект `UIApplication`,
который стоит в цепочке **после** окна. Если не вызвать `super`,
событие на окне и закончится, и «встряхни, чтобы отменить» перестанет
работать во всём приложении.

> **Идея.** Окно — одно из последних звеньев responder chain. Всё, что
> не обработали экраны, доходит до него. Поэтому окно — удобное место
> для глобальных реакций: встряхивание, сочетания клавиш на iPad с
> клавиатурой и тому подобное.

## 3.3 Responder chain — коротко

**Responder** (англ. «отвечающий») — любой объект-наследник
`UIResponder`, который умеет получать события: касания, нажатия
клавиш, движения. Наследники `UIResponder` — это `UIView`,
`UIViewController`, `UIWindow`, `UIApplication` и даже `UIWindowScene`.

**Responder chain** (цепочка ответчиков) — порядок, в котором событие
передаётся от одного ответчика к другому, если первый его не
обработал. У каждого ответчика есть свойство `next` — «кому передать
дальше». Правила такие (документация Apple, «Using responders and the
responder chain»):

- у view дальше идёт его родительский view; а если view — корневой
  view экрана, то сам view controller;
- у view controller'а — родительский view его view (или окно,
  если экран — корневой в окне; или экран, который его показал, если
  он показан модально);
- у окна — сцена, у сцены — `UIApplication`;
- у `UIApplication` — делегат приложения (`AppDelegate`), если он
  наследник `UIResponder`.

**First responder** (первый ответчик) — тот, кому событие достаётся
первым. Для касания это view, по которому попал палец. Для клавиатуры
и встряхивания — объект, который сейчас «в фокусе»: например,
текстовое поле, в котором мигает курсор. Когда такого объекта нет,
UIKit начинает с окна.

Чтобы не гадать, мы распечатали цепочку в нашем собранном playground'е
(как — в упражнении 3.2). От таблицы лаунчера она такая:

```
UITableView
 → AppListViewController
 → UIViewControllerWrapperView        ┐
 → UINavigationTransitionView         │ служебные view
 → UILayoutContainerView              ┘ UINavigationController
 → UINavigationController
 → UIDropShadowView                   ┐ служебные view,
 → UITransitionView                   ┘ которые окно держит под root
 → PlaygroundWindow                   ← здесь ловим мы
 → UIWindowScene
 → UIApplication                      ← здесь работает «встряхни для отмены»
 → AppDelegate
```

Классы с незнакомыми именами (`UIViewControllerWrapperView`,
`UITransitionView`…) — внутренние view UIKit, их не создают вручную.
Важно другое: какой бы экран ни был открыт, событие, которое никто не
обработал, **обязательно дойдёт до окна**.

Каждое звено может «съесть» событие или передать дальше. Мы ловим **в
окне**, потому что:

- окно одно и существует всё время, пока приложение открыто, — а
  конкретный экран mini-app появляется и исчезает;
- подписываться нужно в одном месте, а не в каждом из десятка экранов.

Альтернативы есть: рассылать «было встряхивание» через
`NotificationCenter` (общую «доску объявлений» приложения) или сделать
протокол, который реализует каждый экран. Оба варианта работают, но
требуют дисциплины: забыл подписать экран — жест на нём не работает. С
окном забыть нельзя.

`super.motionEnded(motion, with: event)`. Что сломается и в какой

## 3.4 Кто устанавливает `onShake`

Сам `PlaygroundWindow` не знает, что делать при встряхивании. Решает
**`BootCoordinator`** (глава 4): когда запускает mini-app, он кладёт
в окно callback:

```swift
// фрагмент из BootCoordinator.start()
window?.onShake = { [weak self] in
    self?.exitToLauncher()
}
```

А при выходе в лаунчер — убирает его:

```swift
// фрагмент из BootCoordinator
private func exitToLauncher() {
    window?.onShake = nil
    // ...
    onExit()
}
```

После этого встряхивание в лаунчере ничего не делает. Так и задумано:
из лаунчера выходить некуда.

> **Внимание: `[weak self]` здесь обязателен.** Окно держит замыкание
> (свойство `onShake`), замыкание держит координатор. Если координатор
> захвачен **сильно**, то, пока окно живо (а оно живо всё время),
> координатор не освободится, даже когда его никто больше не
> использует. Это **утечка памяти**: объект висит в памяти, хотя уже не
> нужен. С `[weak self]` замыкание не удерживает координатор: когда его
> отпустят, `self` внутри станет `nil`, и вызов `self?.exitToLauncher()`
> просто ничего не сделает.

## 3.5 Где создаётся окно

В `SceneDelegate.swift` (целиком разберём его в главе 5):

```swift
func scene(_ scene: UIScene,
           willConnectTo session: UISceneSession,
           options connectionOptions: UIScene.ConnectionOptions) {
    guard let windowScene = scene as? UIWindowScene else { return }

    let window = PlaygroundWindow(windowScene: windowScene)
    // ... здесь создаём лаунчер и ставим его rootViewController'ом ...
    window.makeKeyAndVisible()
    self.window = window
}
```

`PlaygroundWindow(windowScene:)` — инициализатор `UIWindow`, который
сразу привязывает окно к сцене. Наш класс его не переопределяет, а
наследует, поэтому интерфейс тот же, что у обычного окна.

`makeKeyAndVisible()` — делает окно **ключевым** (key window: именно
оно получает ввод с клавиатуры и события без конкретной точки
касания) и показывает его. Без этого вызова окно останется
невидимым.

`self.window = window` — сохраняем **сильную ссылку** на окно в
свойстве `SceneDelegate`. UIKit сам окно не удерживает. Если не
сохранить ссылку, окно освободится сразу после выхода из метода —
приложение не упадёт, но экран останется чёрным.

## 3.6 Как проверить встряхивание в симуляторе

Физически потрясти симулятор нельзя, поэтому:

- меню симулятора **Device → Shake**;
- сочетание клавиш **⌃⌘Z** (Control + Command + Z).

Фокус должен быть на окне симулятора. Если нажать ⌘Z в Xcode — это
будет «Отменить» в редакторе кода, а не встряхивание.

На устройстве — просто встряхни iPhone.

Два нюанса этого жеста.

**Его никто не знает.** Пользователь не догадается, что для выхода
надо трясти телефон. Поэтому в лаунчере под списком мы пишем подсказку
(глава 4), а в заглушке «ещё не реализовано» — прямо текстом.

**Он пересекается со «встряхни для отмены».** Если в mini-app открыто
текстовое поле с набранным текстом, встряхивание вызовет и нашу
реакцию, и системную: окно уйдёт в лаунчер, а система предложит
отменить ввод. Для учебного playground'а это приемлемо. В настоящем
приложении встряхивание для навигации лучше не использовать — только
для отладочных функций вроде «отправить отчёт об ошибке».

**Упражнение 3.2.** Напиши функцию, которая печатает цепочку
ответчиков от любого view до конца — через свойство `next`, — и
вызови её из `viewDidAppear` заглушки `PlaceholderViewController`
для её `view`. Что окажется между экраном и окном, если mini-app
показано внутри `UINavigationController`?

## 3.7 Бытовая аналогия

Окно — **ресепшен в офисном здании**. Экраны — **кабинеты**. Позвонили
в здание — звонок сначала попадает в тот кабинет, куда звонили. Если
там не берут, звонок переводят выше по цепочке: начальнику отдела,
потом на ресепшен. Ресепшен — одна из последних инстанций: он есть
всегда, какие бы кабинеты ни открывались и закрывались.

Поэтому общую для всего здания инструкцию «если позвонили с кодовым
словом — проводить гостя к выходу» даём ресепшену, а не каждому
кабинету.

## 3.8 Что можно было бы сделать вместо встряхивания

Способов «вернуться в лаунчер» несколько:

- **Системный жест «домой»** (свайп вверх от нижнего края) —
  сворачивает приложение целиком, а не возвращает на наш экран.
  Перехватить его нельзя.
- **Свайп от левого края** — работает только внутри стопки
  `UINavigationController`, а mini-app у нас — отдельный корневой
  экран.
- **Кнопка в углу** поверх каждого mini-app — работает и понятна, но
  вмешивается в дизайн каждого экрана.
- **Встряхивание** — не требует элементов на экране, не конфликтует с
  интерфейсом mini-app, в симуляторе есть сочетание клавиш.

Встряхивание — компромисс. В приложении для App Store я бы так не
делал: жест неочевиден. Для учебного playground'а он подходит лучше
всего: не требует UI-элементов и не портит дизайн mini-app.

## Ответы к упражнениям

**3.1.** Встряхивание перестанет доходить до `UIApplication`, а именно
он показывает системное «Отменить ввод?». Пользователь заметит это,
когда наберёт текст в любом поле ввода и встряхнёт телефон: алерта с
отменой не будет. Наш выход в лаунчер при этом работать продолжит —
`onShake` вызывается после `super`, и от него не зависит.

**3.2.** Функция — обход по `next`, пока он не станет `nil`:

```swift
func printResponderChain(from responder: UIResponder) {
    let chain = sequence(first: responder, next: { $0.next })
        .map { String(describing: type(of: $0)) }
        .joined(separator: " → ")
    print(chain)
}
```

`sequence(first:next:)` — стандартная функция Swift: берёт первый
элемент и правило «как получить очередной» и выдаёт последовательность
до первого `nil`. `type(of:)` возвращает класс объекта, а
`String(describing:)` превращает его в имя.

Вызов в `PlaceholderViewController`:

```swift
    override func viewDidAppear(_ animated: Bool) {
        super.viewDidAppear(animated)
        printResponderChain(from: view)
    }
```

В нашем playground'е печатается:

```
UIView → PlaceholderViewController → UIViewControllerWrapperView
→ UINavigationTransitionView → UILayoutContainerView
→ UINavigationController → UIDropShadowView → UITransitionView
→ PlaygroundWindow → UIWindowScene → UIApplication → AppDelegate
```

Между экраном и окном — `UINavigationController` и его служебные view
(`UIViewControllerWrapperView`, `UINavigationTransitionView`,
`UILayoutContainerView`), а также `UIDropShadowView` и
`UITransitionView`, которые окно держит под корневым экраном. Точный набор служебных классов зависит от
версии iOS — это внутреннее устройство UIKit, полагаться на него в
коде нельзя. Но порядок «экран → контроллер навигации → окно → сцена →
приложение» стабилен.

## Что мы выучили

- `UIWindow` — самый верхний контейнер интерфейса, «рама» для
  `rootViewController`. Принадлежит сцене. Обычно его не трогают, но
  для глобальных жестов это самое надёжное место.
- **Responder chain** — цепочка передачи событий через `next`: view →
  view controller → … → окно → сцена → `UIApplication` → `AppDelegate`.
  **First responder** получает событие первым.
- `motionEnded(_:with:)` — метод `UIResponder`, который вызывается по
  окончании встряхивания. Проверяем `motion == .motionShake`.
- Всегда вызывай `super.motionEnded(...)` — иначе сломается системное
  «встряхни для отмены».
- `onShake` ставит `BootCoordinator` при входе в mini-app и сбрасывает
  при выходе. `[weak self]` в этом замыкании обязателен — иначе окно
  удержит координатор навсегда.
- Окно нужно сохранить в `SceneDelegate.window` и показать через
  `makeKeyAndVisible()`, иначе экран будет чёрным.
- В симуляторе встряхивание — ⌃⌘Z или Device → Shake.
